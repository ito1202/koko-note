# セキュリティ

## 保護対象と限界

本文とタイトルはWindows DPAPI CurrentUserで個別に暗号化します。`CRYPTPROTECT_UI_FORBIDDEN` を指定し、`CRYPTPROTECT_LOCAL_MACHINE` は使用しません。追加エントロピーにスキーマ用識別子・ノートID・フィールド名を含め、別ノートやタイトル／本文間の暗号文の入れ替えも復号エラーにします。このエントロピーは秘密鍵ではありません。

DPAPIは通常、暗号化時と同じWindowsログオン資格情報・端末のキーを必要とします。Windowsプロファイル、DPAPIキー、資格情報の復旧条件に依存するため、DBの別端末・別ユーザーへのコピーを汎用バックアップ／復元手段とは扱いません。OS再インストール、プロファイル消失、管理者によるパスワードリセット等で復元不能になる場合があります。MVPにはパスワード方式のエクスポートや旧Avalonia版からの移行はありません。[MicrosoftのDPAPI仕様](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)を参照してください。

同一Windowsユーザー権限のマルウェアはDPAPIを呼び出せます。管理者、SYSTEM、プロセスメモリの読み取り、画面取得、キーロガー、クラッシュダンプやページファイルまで防げません。ノートは編集と検索のためメモリで復号します。.NETのstringとWindows編集コントロール内の全コピーを確実にゼロ化することも保証しません。暗号化・復号時の一時byte配列とDPAPIの出力バッファの平文は可能な範囲でクリアします。

## SQLiteに平文を渡さない

保存前にタイトル・本文をDPAPIで暗号化し、SQLパラメーターにはBLOBだけを渡します。FTS、平文の索引、本文を含むテンポラリテーブル、平文エクスポートは作りません。検索語もディスクへ保存しません。

| 保存物 | 構成と扱い |
|---|---|
| DB本体 | 暗号化タイトル・本文。ID、時刻、順序、閉じた状態、世代は平文 |
| WAL | `journal_mode=WAL`、`synchronous=FULL`。変更ページ内にも暗号文のみ |
| SHM | WAL索引用。SQLiteへ平文の文字列を渡さない |
| ロールバック／statement journal | ページの退避先。元ページが既に暗号文なので本文平文は入らない |
| 一時領域 | `temp_store=MEMORY`。テキストのソート・全文検索はアプリメモリで実施 |
| バックアップ | SQLite Backup APIでWALを含む整合したページをコピー。内容は暗号文 |
| AppState | ノートID、選択・スクロール座標、ウィンドウ寸法のみ。平文メタデータ |

SQLiteの[一時ファイル](https://sqlite.org/tempfiles.html)と[WAL](https://sqlite.org/wal.html)の仕様を調査しました。ジャーナルを無効にして平文痕跡を減らす方法はデータ耐久性を下げるため採用していません。`secure_delete=ON` も指定しますが、WALやSSDの履歴まで暗号文を物理消去できるとは主張しません。暗号文の長さ、ノート数、編集時刻などのメタデータは観測可能です。

自動テストは既知の長いマーカーを本文・タイトルに保存し、保持中のWAL、DB、SHM、Backup APIの出力をUTF-8／UTF-16で走査します。BLOB型も検査します。macOSではテスト専用AES-GCMでこの保存境界を検証し、実DPAPIを使う同じ検査はWindows専用です。これは全てのOS一時ファイルやメモリページを網羅する証明ではありません。ロールバックの実動作は別のトリガー障害テストで検証します。実行結果は[validation.md](validation.md)に記録します。

## ACLとプロセス境界

`%LOCALAPPDATA%\KOKONote` のDACLから継承を外し、現在のユーザーSIDとSYSTEMにFullControlを付与します。新規ファイルに継承させ、既存の直接配下ファイルにも同じ制限を設定します。保存先や直接配下の再解析ポイント、想定外のサブディレクトリは拒否します。ACL設定に失敗した場合は起動しません。管理者の所有権取得、同一ユーザーによる書き換えやTOCTOU攻撃に対する境界とは扱いません。Windows上のACL実検証は未実施です。

ユーザーSID付きMutexと、保存先の排他的ロックファイルで多重起動を防ぎます。ロックファイルの存在自体は起動拒否の理由になりません。クラッシュ後はOSがハンドルを解放します。権限昇格は要求しません。

## 失敗・破損と移行

復号エラー時はそのノートを空文字列として読み込まず、全体のロードを中断します。保存可能なWorkspaceを構築しないため、誤った鍵で空データが上書きされません。SQLiteの `quick_check`、スキーマバージョン、状態JSONも検査します。DPAPIエラー・DBエラーのダイアログは定型文で、本文・タイトル・SQLパラメーター・例外の詳細を含みません。ログファイルを作りません。

SQLの値はパラメーター化しています。`trusted_schema=OFF`、接続プール無効、2秒のbusy待機を使います。未知のDB・将来バージョンは自動変換しません。今後の移行はバックアップを必須とします。保存先ディスク故障や悪意のある同一ユーザーによるDB削除、未保存中の強制終了までは保護できません。

## 外部との接点

HTTPクライアント、ソケット、テレメトリSDK、更新チェック、クラウド、WebViewを使いません。NuGet復元は開発時の操作です。クリップボードはユーザーの明示的なコピー／切り取り／貼り付けだけに使い、監視・自動コピーはありません。キー入力注入、他アプリへの貼り付け・自動送信、グローバルキーボードフックは使いません。P/Invokeの `SendMessage` は自アプリの編集コントロールに対してだけ使用します。

依存関係の初回復元ではSQLitePCLRaw 2.1.11の[既知の脆弱性](https://github.com/advisories/GHSA-2m69-gcr7-jv3q)が検出されました。Microsoft.Data.Sqliteを10.0.15、推移依存をSQLitePCLRaw 2.1.13に更新し、監査警告を抑止せずに対処しました。パッケージはlockファイルで固定します。今後の脆弱性がないことまで保証するものではありません。
